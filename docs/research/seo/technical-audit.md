# Technical and on-page SEO audit

Ticket: [youversion/biblehearth#23](https://github.com/youversion/biblehearth/issues/23), "What technical and on-page SEO defects does the site have today". Audited 2026-09-26 against `main` at `20cd0e6`. I read the code and also probed the live site at https://biblehearth.online with `curl`. I did not run `npm run build`: `node_modules` is absent and installing needs the network.

## Answer

- The site's technical base is sound. Canonicals are set, case and alias book slugs 301, trailing slashes 308, noindex URLs stay out of the sitemaps, `lastmod` is real, and robots.txt is valid. **Googlebot is unaffected by robots.txt.** It falls into the `*` group, where only `/read` and `/api/` are disallowed, and Google ignores `Crawl-delay`. The bot blocks name only third-party crawlers.
- The biggest problem is a policy inconsistency. Unbriefed chapter studies are noindexed because their substance is someone else's text. Yet about **59k licensed-Scripture-only reader URLs** are submitted through the 58 locale sitemaps, **~31k verse hubs** are indexable, and **49 of 66 English book pages** carry no original writing. All of these fall under the same reasoning.
- **Verse hubs never link to their chapter study, and their breadcrumb skips it.** This is confirmed live: `/verse/john/3/16` has no link to the briefed `/john/3`. It is the cheapest internal-link fix available.
- **`<meta charset>` sits at byte 1,255, past the 1,024-byte limit, and `Content-Type` carries no charset.** Lighthouse fails this check, and pages in non-Latin locales are exposed to mis-sniffed encoding. It is a one-line fix.
- The ticket's premises check out as follows:
  - **Confirmed:** chapter descriptions are cut at 300 characters. Google says length doesn't matter, but Bing flags anything over 160.
  - **Confirmed:** `sitemap-bible/[version].xml` is not in the index. That is correct, because it is a dead duplicate of the locale sitemaps.
  - **Confirmed:** every page uses `og-default.png`, because no editorial figures exist yet.
  - **FAQPage markup is harmless but earns nothing.** Google stopped showing FAQ rich results for every site on 2026-05-07, which goes further than the 2023 restriction the ticket describes.
- Other real but smaller defects:
  - The home page returns 503 when the upstream fails.
  - Degraded study and book pages are cached for a day.
  - The "next verse" link on the last verse of every chapter points at a 404.
  - Localized briefs have no crawlable internal path to them.
- Core Web Vitals risk is low. There are no web fonts, no images, one 18 KB stylesheet and edge-cached HTML (TTFB ~150–200 ms when cached, ~0.9 s cold). The main costs are four analytics scripts and full-body buffering in middleware.

## Details

### Premises from the ticket

**1. "Meta descriptions on briefed chapters are cut at 300, not DESCRIPTION_MAX (155)": confirmed, and deliberate.** `[chapter].astro:359-360` calls `truncateWords(brief.data.shortAnswer, 300)`, and the comment at `:355-358` explains it as intended ("Google truncates the display and never penalises the extra"). Google agrees: "There's no limit on how long a meta description can be, but the snippet is truncated in Google Search results as needed." Because the `shortAnswer` schema (`content.config.ts:232`) allows 200–750 characters and the real range is 333–520, every briefed chapter ships ~300. Topics and answers use 155 (`topics/[slug].astro:148-154`, `answers/[slug].astro:135`). The only real cost is on Bing. Its SEO Reports rule "The description is too long or too short" asks for 25–160 characters (secondary sources below; Bing's help pages aren't fetchable). The site otherwise sizes titles to Bing's 65-character window (`seo.ts:127-134`), so this is an inconsistency rather than a Google defect. Fix: pass `DESCRIPTION_MAX` and rely on the front-loaded first sentence, or accept the Bing warning knowingly.

**2. "`sitemap-bible/[version].xml` exists but isn't in `sitemap.xml`": confirmed, and it should stay out.** The route works live (`/sitemap-bible/niv.xml` → 200), but nothing links to it. `versionSitemapPath` is only used by the route's own self-redirect (`lib/sitemap.ts:20-22`, `sitemap-bible/[version].xml.ts:26`). Its content (`bibleSitemapPaths`) is exactly what `/sitemap-locale/en.xml` already submits for the default version (1,256 URLs live), so adding it to the index would either duplicate that or, for the other English versions, multiply reader URLs ×20. Treat it as dead code: delete it, or leave it unlisted. The underlying problem is defect #1, not the missing entry.

**3. "Verse hubs don't link to their chapter study page, and their breadcrumb skips it": confirmed.** The JSON-LD breadcrumb is `BibleHearth → {Book} (study book page) → {Verse}` (`[verse].astro:194-198`), and the visible crumbs match (`:216-222`). Per-translation links go only to reader chapter and version pages (`:249-256`). The live page's full internal-link list contains `/john` but no `/john/3`. Google recommends that breadcrumbs "represent a typical user path to a page", and Home → Book → Chapter → Verse is that path. Fix: add `{ name: 'John 3', path: chapterStudyPath(bookUsfm, chapterId) }` to both crumbs and a "Study John 3" link. The link is more valuable when the chapter is briefed, but because a crumb reflects the hierarchy it is fine even when the target is noindex (noindex, follow). Note that since January 2025 Google shows breadcrumbs on desktop only, so the markup's SERP value is desktop-only. The internal link is the bigger win.

**4. "Every page shares `public/og-default.png`": confirmed.** The figure pipeline is complete (`lib/images/og.ts` makes 1200×630 JPG crops, and `articleShareFields` passes them to `Article.image`), but there is no content for it to work on. `src/assets/editorial/{answers,chapters,hubs,topics}/` hold only `.gitkeep`, no content file has a `figure:` key, and `hubFigures = {}`. `og-default.png` is 1200×630, so the hard-coded `og:image:width/height` (`BaseLayout.astro:242-243`) is currently accurate. Google's Article guidance asks for images that represent the content, at least 50k pixels, ideally in 16:9, 4:3 and 1:1. A brand card on all 63 editorial pages satisfies the size requirement and misses the "represents the content" one. Impact is on social and chat unfurls and Discover-style surfaces, not ranking.

**5. FAQPage: harmless, and it now earns nothing on Google for anyone.** The premise is out of date. Google restricted FAQ rich results to "well-known, authoritative government and health websites" in August 2023, added a deprecation notice on 2026-05-08 ("will no longer appear in Google Search starting May 7, 2026"), and removed the documentation on 2026-06-15 ("The FAQ rich result feature is no longer shown in Google Search results"). The code comment at `seo.ts:389-393` already says this correctly. Is the markup harmful? No. It is valid schema.org, and the Q&A is visible on the page (`ChapterBriefBody.astro:177-190`, `topics/[slug].astro:266-278`), so there is no hidden-content mismatch under Google's structured-data policies. Google's deprecations make unsupported types ineffective rather than penalized. It costs a few KB per page. Keep it if the team values the retrieval and answer-engine argument in the comment; otherwise drop it. Either way it isn't a defect.

**6. robots.txt and Googlebot: Googlebot is unaffected.** Groups are at `public/robots.txt:8-12` (`*`: Allow `/`, Disallow `/read`, `/api/`, Crawl-delay 5), `:27-31` (bingbot, Crawl-delay 1, Disallows repeated) and `:39-56` (AhrefsBot with an Allow for the IndexNow key, SemrushBot, DataForSeoBot, MJ12bot, DotBot and BLEXBot all `Disallow: /`). No group names Googlebot, so under Google's rule ("the group with the most specific user agent that matches") it uses `*`. Google says "other fields such as `crawl-delay` aren't supported", so the 5-second delay doesn't apply. The blocked bots are third-party SEO crawlers with no bearing on Google. Nothing Googlebot needs for rendering is under `/api/`: Vercel analytics is `/_vercel/insights` and images are `/_vercel/image`. Two side notes:
- `Crawl-delay: 5` also paces AI and answer-engine crawlers that honour it to ~17k URLs a day, against ~60k submitted URLs (plus ~31k crawlable verse hubs).
- `src/lib/http.ts:80-83` says "Googlebot honours `Retry-After` on a 503". Google's HTTP-errors and reduce-crawl-rate docs don't document `Retry-After`. They say 5xx and 429 slow crawling, and warn that doing this for "longer than 1-2 days" can hurt visibility. The header is harmless, but the comment overstates what Google documents.

**7. Book pages indexable for all 66 English books: yes, a real but bounded thin-content risk.** English book pages are indexable unconditionally (`[book]/index.astro:117`) and all 66 are submitted (`sitemap-commentary.xml.ts:99-101`). The justification is the "licensed book overviews" (`:107-116`, `sitemap-commentary.xml.ts:56-63`). Those are the Tyndale, Matthew Henry and JFB introductions, and CLAUDE.md's own reasoning for noindexing unbriefed chapters says they are "already mirrored" by four larger sites. The page's own writing is two templated sentences (`:163-172`). The grid links mainly to noindex pages (17 of 66 books have any brief, so 49 book pages have none), and the title says "Summary" (`:129`). If the overview fetch fails, the page is a 200 with a grid and an error box, cached for a day (`:84,260-265`). Google's spam policy lists "republishing others' content without original additions" under scraping. At 66 pages this is a site-quality drag rather than scaled abuse. Recommendation: make English book pages follow the localized rule (`briefedCount > 0`), or write a 100–200-word original intro per book (the cheapest way to earn the 49), and drop "Summary" from the title until a summary exists.

### Other items requested

**Core Web Vitals risk: low overall.**
- *Render-blocking:* one stylesheet (`/_astro/BaseLayout.*.css`, ~18 KB source) and no inline blocking JS. gtag and Ahrefs are `async`, and Clarity is a module script (deferred) that injects `clarity.ms` (`BaseLayout.astro:161-181`).
- *Fonts:* none are loaded. The stacks are system fonts (`global.css:10-11`: Iowan/Palatino/Georgia, Source Sans 3 if installed, then Segoe/system-ui), so there is no FOIT/FOUT or font CLS.
- *Images:* the live study page has zero `<img>`. The wordmark is inline SVG with width and height (`Header.astro:20-34`), and `Figure.astro` uses `astro:assets` `<Image>` with `widths`/`sizes`. CLS risk is minimal.
- *INP:* the main risk. Four analytics runtimes run on every page (GA4, Ahrefs, Clarity session recording, Vercel Web Analytics plus the delegated listener in `Analytics.astro`). Clarity's DOM recording on 58 KB study pages with three commentary `<details>` is the heaviest.
- *TTFB/LCP:* measured live, cached HITs return in 0.15–0.20 s and a cold verse hub (`/verse/obadiah/1/9`, MISS) in 0.88 s. `middleware.ts:104-115` buffers every HTML 200 to hash an ETag, so nothing streams and TTFB equals full render time on a miss. Vercel purges the edge per deploy (`http.ts:13-14`), so after each deploy every URL is an SSR miss until re-requested. The runtime data cache survives deploys, which keeps those misses off the upstream.
- */api/warm:* runs every 10 minutes (`vercel.json`), 12 chapters per run within a 30 s budget (`api/warm.ts:40,47`). That is ~1,728 chapter fetches a day, enough to cycle the default version's 1,189 chapters in under a day. It warms only the **runtime data cache** for the **default English version**. It does not warm edge HTML, the other five hub translations, or any locale. It protects the app key, not CWV. Its cost is 144 function invocations a day, which is modest. CrUX field data comes from real users, who mostly hit edge-cached pages, so the cron has little CWV effect either way.

**Internal-link depth: 3 clicks or fewer, yes.** Home links the first 8 briefs directly (`index.astro:133-140`), one click. `/study` is in the header nav on every page (`Header.astro:53`) and lists every English brief (`study.astro:108-128`), so every English briefed chapter is at most 2 clicks from home. Two caveats:
- The home 8 are the first 8 by USFM code (`listChapterBriefs` sorts by `usfm`, `lib/commentary/index.ts:101-103`): 1CO.13, ECC.3, EPH.6, GAL.5, GEN.1, GEN.6, HEB.11, ISA.41. The sort is alphabetical, not by priority, so Psalm 23 and John 3 are not on the home page.
- Localized briefs (`/pt/salmo/23`, `/pt/salmo/91`, `/es/salmo/91`) have **no anchor path from home at all** (defect #6).

**Structured-data validity: valid, with minor notes.**
- `Article` (`seo.ts:296-387`): Google's Article type has no required properties. `author` is an `Organization` with `@id`, `name` and `url`, which is acceptable ("Use the Organization type for organizations"). `publisher` is an `@id` reference that resolves to the author node in the same document (`seo.ts:357-361`), and the full node with a 180×180 logo is on /about (`seo.ts:452-482`). `datePublished`/`dateModified` are ISO 8601 with `Z` via `toISOString()`, which satisfies Google's timezone recommendation. They match `article:*_time` (`BaseLayout.astro:223-238`) and `Last-Modified` (live: `last-modified: Fri, 21 Aug 2026 00:00:00 GMT` on `/psalms/28`). The visible date is month-only ("reviewed August 2026", `[chapter].astro:433-438,658-667`), which is acceptable. `image` is the generic card (#11). If a named human writer is ever credited, a `Person` author with a `url` is what Google's E-E-A-T-oriented guidance favours, and `seo.ts:423-431` already anticipates this.
- `BreadcrumbList` (`seo.ts:236-250`): valid, with absolute URLs, positions and the last item carrying `item` (optional per Google). The defects are in the content of verse-hub crumbs (#2) and localized crumbs pointing at `/pt/study`, which canonicalizes away (#6). Reader crumbs name the last item "Chapter N" rather than the reference, which is harmless.
- The study page emits Breadcrumb, Article, three `CreativeWork` citations nested in Article, and FAQPage (live). Unbriefed chapters and book pages emit `CreativeWork` (`[chapter].astro:415-423`), which is fine.
- JSON-LD is serialized with `JSON.stringify` into `<script>` without escaping `</` (`BaseLayout.astro:250-254`). That is safe while all input is first-party content, but worth hardening.
- VOTD `Article` with a daily `datePublished` (#15).

**Duplicate titles.** No duplicates within indexable templates:
- Chapter titles come from `seoTitle`/`title`, 31–59 characters.
- Topics: "N Bible Verses About X, Grouped and Explained", 48–55 characters.
- Answers: "{question} Meaning and N Main Views", 54–65 characters. At 65, "What Does the Bible Say About Cremation? Meaning and 3 Main Views" sits exactly at `TITLE_MAX`, and `answers/[slug].astro:124` has no guard: a longer question would overrun.
- Reader titles include the version abbreviation.

The meaningful duplication is in content, not titles: study vs reader chapter (#5), and reader pages vs bible.com (#1).

**Canonical edge cases.**
- Book aliases and case (`/Psalms/28`, `/psa/28`) → 301 to `/psalms/28` (live).
- Trailing slash → 308 to the slashless URL (live, consistent with `trailingSlash: 'never'` and Astro 5.2+ on-demand trailing-slash redirects).
- Locale search slugs → 301 (`/pt/salmos/23` → `/pt/salmo/23`, live).
- `/pt/study` → 200 with canonical `/study` (English content on a `/pt/` URL, #6).
- Zero-padded numbers and verse-hub case (#13).
- Markdown twins are `X-Robots-Tag: noindex` and 404 without a brief (`lib/markdown.ts:322,338-342`), as documented.

**404 vs soft-404 for unbriefed chapters: handled correctly in the steady state.**
- An unbriefed chapter with commentary → 200 plus `noindex, follow`, out of the sitemap. That is not a soft 404, because the page has real content.
- Out-of-range chapter, missing book in a locale, or no commentary and no brief → rewrite to `/404` with real status 404, `noindex`, cached 1 day (`[chapter].astro:107-114,208-210`; `404.astro:6-7`).
- Unmatched paths → `[...fallback].astro` → 404.

The gaps are transient states: commentary-API failure → a cached 404 (#10), and a book page with failed overviews → a 200 soft-404-like page cached for a day (#8). Reader and hub pages return 503 plus `Retry-After` on upstream errors (`lib/http.ts:122-134`), which is correct.
